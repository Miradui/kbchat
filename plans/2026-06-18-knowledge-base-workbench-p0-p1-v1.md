# 知识库工作台 P0/P1 后端计划

## Objective

先把截图所需的知识库工作台后端能力补成两层：P0 解决当前页面马上会撞到的身份展示和元数据缺口，P1 补齐标签、回收站、问答管理这类次级模块。范围仍然保持 owner_id 作为唯一权限边界，不引入复杂 RBAC、多租户、SSO 或审计。

当前基础工作台能力已经存在于 `backend/internal/router/router.go:79`、`backend/internal/model/models.go:29` 和 `docs/04-api-design.md:147`，而 `docs/12-handoff.md:153` 仍把标签、回收站和更复杂权限列为后续项，所以这份计划只围绕“还缺什么”继续往前推。

## Implementation Plan

- [ ] 1. 先冻结 P0 和 P1 的边界，并把现有工作台接口、模型和文档缺口对齐到同一份清单里，避免后面在标签、回收站、问答管理之间来回改方向；这一项的目标是把当前已存在的 `/knowledge-bases`、`/documents`、`/search` 和 `/chat` 能力分成“现在就补”和“以后再补”两组。
- [ ] 2. P0 先补用户身份展示所需的数据面，给 `auth/me` 和相关 DTO 增加头像或等价展示字段，同时确认前端顶栏、用户菜单和工作台卡片能从同一条用户信息链路拿到足够数据，减少前端临时拼装。
- [ ] 3. P0 再补知识库“最后更新人”的真实来源，把知识库的更新人写入持久层并回填到列表和详情响应里；这一项重点是让工作台卡片能直接展示谁最后改过知识库，而不是只看更新时间。
- [ ] 4. P0 把当前工作台卡片和详情页依赖的动作信息整理完整，确保收藏、最近浏览、分类归属、展示状态和常用操作都能从后端返回稳定字段，不再依赖前端猜测哪些按钮该显示。
- [ ] 5. P1 新增标签模块，先把知识库标签的基础表结构、标签 CRUD、知识库与标签的关联关系做出来，再补列表筛选和详情展示；这一阶段只做 owner 范围内的标签管理，不扩展成跨用户协作标签。
- [ ] 6. P1 新增回收站模块，针对知识库和文档补软删除、恢复、彻底删除和回收站列表能力；这一项要优先梳理和现有硬删除、级联清理、聊天会话清理之间的边界，避免恢复后数据不一致。
- [ ] 7. P1 新增问答管理模块，让后台可以按当前用户知识库查看会话、按关键词或知识库过滤问答记录，并支持重命名、删除、归档这类管理动作；这部分复用现有聊天链路，但不把它改造成新的问答引擎。
- [ ] 8. 把上述两层能力同步落到 migration、GORM model、repository、service、handler、router 和测试里，并补齐 API 文档与交接文档，保证前端联调时不会因为字段断裂或响应形状变化反复返工。

## Verification Criteria

- P0 完成后，`/auth/me` 能返回前端顶栏需要的用户展示字段，知识库列表和详情能直接返回 `updatedBy` 等展示信息。
- P0 完成后，工作台首页不需要额外请求就能渲染知识库卡片的核心信息，至少包括分类、收藏、最近浏览和更新人。
- P1 完成后，标签、回收站、问答管理三个模块都有对应的后端入口，并且所有查询和写入都只能作用于当前用户拥有的知识库资源。
- 关键验证命令仍然保持通过：`cd backend; go test ./...`、`cd backend; go run ./cmd/migrate`、`cd backend; go run ./cmd/doctor`。

## Potential Risks and Mitigations

1. **更新人字段和标签表会扩大 schema 变更面**
   Mitigation: 把 P0 和 P1 拆成独立 migration，优先加可空字段和兼容默认值，避免把旧接口一次性打断。

2. **回收站和现有硬删除语义可能冲突**
   Mitigation: 先明确哪些对象走软删除、哪些对象继续硬删除，再让恢复能力只覆盖真正需要 UI 回收站的资源。

3. **问答管理可能和现有 chat sessions 接口重叠**
   Mitigation: 复用现有聊天会话表和消息表，只在服务层补管理型查询与状态变更，不再引入第二套会话模型。

## Alternative Approaches

1. **推荐方案：P0 先轻量补齐，P1 再拆模块推进**。优点是最贴合当前截图落地节奏，风险小，也方便前端先接住能展示的内容；缺点是标签和回收站不会一次到位。
2. **一次性把 P0 和 P1 的 schema 都补完**。优点是后面少改 migration，缺点是反馈周期更长，容易把还不确定的 UI 需求过早固化。
3. **只做 P0，P1 暂缓**。优点是最快看到页面主链路，缺点是后台管理面会明显偏瘦，后面还是要补第二轮接口。
