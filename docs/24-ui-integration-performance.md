## PDF 引用高亮

`PdfPreview` 接收可选引用目标，仅在有效引用页匹配完整摘录。基于 PDF.js 文本层建立原文字符映射，统一全半角、连字、组合字素和排版空白；保留标点与大小写。后端 PDF 字节偏移与 PDF.js 提取顺序不同，因此不用于定位。

唯一匹配时标记原始文字，支持同页切换、跨页切换、缩放、手动翻页后返回引用。只滚动 PDF 内部区域，不在异步渲染结束时移动焦点。无法匹配、存在多个相同位置、页码缺失或越界时明确提示并保留引用摘录，不猜测位置。只读成员的原文件权限保持原合同。

浏览器使用合成会话消息提供七种引用，文档元数据、鉴权和 PDF 字节来自本轮真实后端。1920×1080 检查中文整句高亮、原文选择、同页切换不重绘画布、缩放与跨页定位、明暗主题及四类退路均通过；同一文件切换所有引用仅下载一次，未捕获页面异常。该验证不代表模型生成这些引用的链路已通过。

| 场景 | 最后一个 delta 至 done，中位数 |
| --- | --- |
| 标题立即失败并保留摘要 | 1.070 ms |
| 标题 Provider 固定延迟 500 ms 后成功 | 501.312 ms |

10 个子用例均通过。标题同步调用会拖延收尾，但当前配置没有标题网络等待；本轮保留“启用标题模型并观察到明显延迟后再异步化”的条件项，不引入后台任务或前端轮询。这些数据仅来自本地 SSE service 夹具，不代表真实数据库、HTTP 或模型性能。

## 长会话性能

本轮基线固定为提交 `d9e3f16` 的 257 个前端源码文件。改前/改后均使用生产 React profiling 构建、关闭 StrictMode，在 1920×1080 下交替采样；依赖锁、合成数据与采集脚本相同。20 / 200 条历史消息各运行改前、改后各三次，共 12 个样本。每次回复包含 400 次 delta、每次 20 字符，目标间隔 20 ms；接口响应重新序列化/解析，模拟实际 JSON 响应产生新对象。

问题集中在发送开始和结束刷新时：历史消息对象变化使未改变的 Markdown 正文再次解析。`ChatMarkdown` 将正文解析放入 memo 子组件，仅依赖正文与有效引用数量；外层 Context 继续更新引用元数据、当前焦点和点击回调，避免保留旧引用。未引入虚拟列表或修改消息列表结构。

| --- | --- | --- | --- |

200 条历史的累计 React 渲染耗时减少约 46.3%，三轮改后均未出现长任务；短会话总渲染耗时基本持平。Layout 耗时未明显下降，最大帧间隔仍有 60.6 ms，不能据此宣称全部卡顿消失。改前有一轮出现 11 个长任务，保留逐轮原始数据，不删除波动样本。

额外的 200 条历史交互检查通过：流式中查找及跳到下一结果、保留用户滚动位置、回到底部后恢复跟随（底部距离 60 px，阈值 80 px）、最终回答与全部 delta 一致、完成后继续编辑输入框；无意外请求或运行异常。引用元数据、焦点、回调切换与流式正文更新由组件回归覆盖。

采样机器为 Windows（系统版本 10.0.22000）、Ryzen 7 5800H、16 GB 内存、Node v24.6.0。React Profiler 不包含完整布局和绘制成本，Layout 为 CDP 独立指标；主线程定时器会被负载延后，JSON 克隆不模拟网络延迟。本轮仅证明固定本地夹具的渲染改善，不代表模型吞吐、真实网络或所有设备性能。
