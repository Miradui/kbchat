日期：2026-10-20。范围：当前工作区后端、前端、SQL 迁移与文档，包含尚未提交的改动。

方式：只读审计。未修改源码，未连接业务库，未启动服务，未执行迁移。缺陷编号固定为 `AUD-*`，后续修复与复验沿用同一编号；本轮只登记，不关闭任何条目。

## 结论

核心链路质量高于一般 MVP：会话归属与逐库鉴权、发送落库事务与幂等、引用与 Prompt 同源、`answerStatus` 状态机、迁移 048 的 `general` 在常量/解析/Prompt/约束/启动检查五处一致，未发现可用的越权读取路径。

主要风险集中在四处：

1. 不可信文档输入上有一个可打挂进程的切片 panic（`AUD-001`）。
2. 跨行不变量的并发保护不足：最后管理员、知识库所有权（`AUD-002`、`AUD-005`）。
3. 启动期 `AutoMigrate` 绕过 SQL 迁移，schema 可在部署间漂移（`AUD-003`）。
4. 归档只读语义、范围失效状态码、用量与 provenance 落库在多条路径上不一致（`AUD-004`、`AUD-006` 至 `AUD-010`）。

另有 25 条中低优先级缺陷（P2 18 条、P3 7 条）、12 条文档漂移、10 条优化项和 8 条功能建议，分别列在下面。

## 缺陷账本

级别定义：P0 可导致进程退出或数据不可用；P1 产生错误数据、绕过只读语义或使部署不可重复；P2 有明确用户影响但可绕过；P3 低概率或仅一致性问题。全部为 open。

### P0

#### AUD-001 超宽 Markdown/DOCX 表格切片 panic，worker 无 recover，整个后端退出

- 位置：[splitter.go](../backend/internal/document/splitter/splitter.go#L1215) 的 `for _, span := range spans[1:]`；空切片来源是 `splitTextToBudgetSpans` 对纯空白返回 `nil`（[:1088](../backend/internal/document/splitter/splitter.go#L1088)），调用点是 `plainTableCellParts`（[:1245](../backend/internal/document/splitter/splitter.go#L1245)）。
- 触发：表格行超过 chunk 预算（约 800 token）后逐单元格切分（[:904](../backend/internal/document/splitter/splitter.go#L904)），任一单元格含两个行内代码串、中间只有空白，例如 `` | 用法 `a` `b` | ``。此时夹层 `" "` 通过 `start < end` 守卫，进入 `spans[1:]`。
- 影响：[worker.go](../backend/internal/job/worker.go#L120) 的处理 goroutine 没有 `recover()`（全仓仅 PDF parser 有两处）。panic 终止整个 Go 进程。任何能在某知识库上传 `.md`/`.docx` 的用户都能触发，属于低成本 DoS。
- 建议：`plainTableCellParts` 对 `strings.TrimSpace(content) == ""` 直接返回；`splitMarkdownTableCellToBudgetSpans` 先判 `len(spans) > 1`；worker 处理 goroutine 加 `defer recover()` 并转成 job failed。补一条“构造超宽表格行 + 双代码单元格”的回归测试。不要只在入口加长度限制，panic 来自切片边界，长度限制挡不住。
- 复核：已读全部路径确认；未写复现用例（写单测即可锁定）。

### P1

#### AUD-002 最后管理员保护是 write-skew，两名管理员可同时互相禁用/降级

- 位置：[user_repository.go](../backend/internal/repository/user_repository.go#L131) 只对目标行 `FOR UPDATE`；计数在 [:213](../backend/internal/repository/user_repository.go#L213) 是普通读，不加锁。禁用与降级两条路径分别在 [:140](../backend/internal/repository/user_repository.go#L140)、[:189](../backend/internal/repository/user_repository.go#L189) 调用。
- 触发：A、B 均为启用 admin，A 禁用/降级 B 的同时 B 对 A 做同样操作。两个事务锁不同行，互不阻塞，都读到对方仍 active 的快照。
- 影响：`role='admin' AND status='active'` 归零，`/admin/users` 与 `/system/diagnostics` 全部 403；[system_admin_repository.go](../backend/internal/repository/system_admin_repository.go#L48) 的 bootstrap 只数 `role='admin'`（不看 status），CLI 恢复也被拒绝，只能直接改库。
- 建议：事务内先锁全部 admin 行（`SELECT id FROM users WHERE role='admin' FOR UPDATE`）或用 `pg_advisory_xact_lock` 再计数；bootstrap 只统计 active 管理员。

#### AUD-003 启动期 AutoMigrate 先建表，SQL 迁移被 `CREATE TABLE IF NOT EXISTS` 跳过

- 位置：[main.go](../backend/cmd/server/main.go#L38) 启动即 `database.AutoMigrate`；[database.go](../backend/internal/database/database.go#L55) 按模型逐表 `CreateTable`，随后 `validateSchema` 只抽查部分列和两张 CHECK。
- 触发：任何“先起 server、后跑 migrate”的环境。AutoMigrate 先建出缺 CHECK/外键的表，`validateSchema` 在 `documents_error_code_check` 上失败退出，留下半成品；再跑 `cmd/migrate`，001 的建表语句全部跳过，`documents_status_check`、`document_jobs_status_check`、`chat_messages_role_check` 与 `ON DELETE CASCADE` 永久缺失。
- 影响：非法状态值可写入；直接 SQL 删父行不再级联；误删的单表会被 server 静默重建并绕过后续迁移的约束；同一版本在不同部署间 schema 不一致。生产账号被迫持有 DDL 权限只是次要后果。
- 建议：server 启动不建表，改为只读断言；如确需本地便利，用显式 `RAG_ALLOW_AUTOMIGRATE` 且仅在非生产生效。`validateSchema` 补 001 的三个 CHECK 与 020 的角色约束。2026-10-20 的启动事故已经演示过这条路径。

#### AUD-004 归档会话仍可写入；自动范围还会 500 并伪造一条 `retrieval_failed`

- 位置：`SendMessage`（[chat_service.go](../backend/internal/service/chat_service.go#L1051)）、`SendMessageStream`（[:1144](../backend/internal/service/chat_service.go#L1144)）、`RegenerateMessage`（[:1348](../backend/internal/service/chat_service.go#L1348)）都没有 `ArchivedAt` 校验；只有 `EditMessageAndRegenerate`（[:1429](../backend/internal/service/chat_service.go#L1429)）拒绝。前端按只读处理（[ChatPage.tsx](../frontend/src/pages/Chat/ChatPage.tsx#L340)、[:435](../frontend/src/pages/Chat/ChatPage.tsx#L435)）。
- 触发：对已归档会话直接调用发送/流式/重生成（旧标签页、脚本，或发送后另一标签页归档）。自动会话命中“尚未登记的库”时会命中 `archived_at IS NULL` 的行锁（[chat_scope.go](../backend/internal/repository/chat_scope.go#L40)），返回 not found，被包成 500。
- 影响：归档会话继续消耗模型额度，与编辑接口和前端语义冲突；500 命中 `isRetrievalInfrastructureFailure` 后会把“知识检索暂时不可用”以 `answer_status=retrieval_failed` 真正写进该会话，把实现 bug 记成检索故障。
- 建议：在 `authorizeSession` 之后加统一的 `AssertWritableSession`，所有写路径复用；`AddSessionKnowledgeBases` 区分“会话不可写”与真实内部错误。

#### AUD-005 知识库更新整行 `Save`，并发转移会把 `owner_id` 写回旧 owner

- 位置：[knowledge_base_repository.go](../backend/internal/repository/knowledge_base_repository.go#L379) 用 `Omit(clause.Associations).Save(kb)`，SET 覆盖包括 `owner_id`、`updated_by_id`、`deleted_at` 在内的全部列；调用点 [knowledge_base_service.go](../backend/internal/service/knowledge_base_service.go#L324)、[:579](../backend/internal/service/knowledge_base_service.go#L579)。转移侧在 [knowledge_base_ownership.go](../backend/internal/repository/knowledge_base_ownership.go#L67) 做带旧 `owner_id` 的 CAS UPDATE，并在 [:70](../backend/internal/repository/knowledge_base_ownership.go#L70) 删除双方成员行。
- 触发：manager 的 `PUT /knowledge-bases/{id}` 或权限更新与 owner 的转让并发，且 Save 在转移提交后落库。
- 影响：`owner_id` 被旧快照覆盖回原 owner；新 owner 立刻 404，原 owner 仍持有该库，activity 却记录“已转移”。`visibility`、`category_id` 同样会被旧快照覆盖。并发软删不会复活记录（GORM 会追加 `deleted_at IS NULL` 并返回 not found）。
- 建议：`Update` 改为列白名单 `Updates(map[string]any{...})`，显式排除 `owner_id`、`deleted_at`、`created_at`；所有权变更保持独立 CAS。

#### AUD-006 `DOCUMENT_SCOPE_UNAVAILABLE` 在检索入口返回 404，前端因此清空整个会话

- 位置：[retrieval/service.go](../backend/internal/retrieval/service.go#L164) 用 `apperror.NotFound` 返回该 code；规范要求 409（[API 设计](04-api-design.md#L9)、[错误码](09-error-codes.md#L7)），聊天侧另一处 [chat_document_scope.go](../backend/internal/service/chat_document_scope.go#L39) 也是 409。前端在 [useChatThread.ts](../frontend/src/pages/Chat/useChatThread.ts#L166) 对任何 403/404 执行 `setMessages([])` 并提示“会话已不可访问”。
- 触发：会话固定了文档范围，其中一份被删除/移动/撤权后，用户继续发送或重新生成。
- 影响：本应提示“重新选择提问范围”，实际清空整段对话并显示访问丢失；用户以为会话被删。检索接口与聊天接口对同一错误给出两种状态码。
- 建议：检索入口改为 409 + 同一 code；若确要保留 404，必须同时改 04/09/10 三处规范并让前端区分该 code 与真正的访问丢失。

### P2

#### AUD-007 重新生成不落 `rerankFallback`

- 位置：[chat_service.go](../backend/internal/service/chat_service.go#L1391) 手工构造 assistant 消息，只调 `applyGeneratedProvenance`；发送路径在 [:1273](../backend/internal/service/chat_service.go#L1273) 写了该列，分支复制也带该列（[chat_branch.go](../backend/internal/repository/chat_branch.go#L115)）。
- 影响：`RERANK_FAILURE_MODE=fallback` 下重新生成，接口当次响应 `used=true`，刷新、消息查询与负反馈明细都显示 null；违反 [数据库设计](03-database-design.md#L364)。
- 建议：让发送/编辑/分支/重生成共用 `buildChatMessagePair` 或抽出 `fillGeneratedFields`，消除字段漂移。

#### AUD-008 provider 未返回 usage 时写入 0 而不是 NULL

- 位置：[chat_service.go](../backend/internal/service/chat_service.go#L2207) 的 `usageTokenValue` 只在 `value < 0` 时返回 nil，而 [chatcore.Usage](../backend/internal/chat/provider.go#L14) 零值为 0，所有调用点都不可能为负。
- 影响：OpenAI 兼容网关不回 usage 时（`include_usage` 未生效、流式 JSON 回退），库里是“真实 0”，与 [数据库设计](03-database-design.md#L534) 的“未返回为 NULL，不估算”相反；0 token 调用同时污染成本与延迟统计。
- 建议：`chatcore.Usage` 增加 `Reported` 标志或改用指针，未报告时写 NULL。

#### AUD-009 阻塞 JSON 路径用回显模型名记录用量

- 位置：[openai.go](../backend/internal/provider/chat/openai.go#L269) 的 `emitBlockingJSON` 使用 `response.Model`；流式 JSON 回退在 [:167](../backend/internal/provider/chat/openai.go#L167) 已被请求模型覆盖，因此影响仅限阻塞路径（`ChatWithOptions`）。
- 影响：服务商常回别名或带日期版本，与 `MODEL_PRICING`、`CHAT_ALLOWED_MODELS` 对不上；[数据库设计](03-database-design.md#L534) 明确不采用回显名。
- 建议：统一用请求 `model`，回显名只用于日志。

#### AUD-010 已消费的 token 在“阻塞降级 + onDelta 失败”时被丢弃

- 位置：[openai.go](../backend/internal/provider/chat/openai.go#L151) 在 fallback 调用成功、`onDelta` 失败时返回 `usage` 与错误；[chat_service.go](../backend/internal/service/chat_service.go#L1783) 在 err 分支直接 return，usage 不落库。
- 影响：`docs/05-rag-pipeline.md` 要求每次模型调用写一条用量；客户端中断且已降级为阻塞时记录缺失。
- 建议：err 分支若 usage 已报告仍调用 `recordUsage`（内部已用 `context.WithoutCancel`，可安全记录）。

#### AUD-011 OCR 校对后 PDF 摘要自相矛盾，接口丢弃整块 OCR

- 位置：[pdf_snapshot.go](../backend/internal/document/parser/pdf_snapshot.go#L68) 的 `TextPages = len(nativePages)`，随后 `PagesWithoutText` 把非原生页（含 OCR 页）全部列入，同时又在 [:75](../backend/internal/document/parser/pdf_snapshot.go#L75) 构造 `OCR.Pages`。消费者 [document_service.go](../backend/internal/service/document_service.go#L919) 判定“OCR 页不应出现在无字页”，不合法就把 `summary.OCR = nil`。
- 触发：任一 PDF 走 `SavePDFCorrection` 后重新处理（processor 优先解码该基线快照），摘要原样写入 `documents.pdf_text_summary`。
- 影响：校对成功的文档在详情接口丢失 OCR 状态和页码，`textPages` 少算 OCR 页，`pagesWithoutText` 把已识别页列为无字，违反 [RAG 链路](05-rag-pipeline.md#L80)。正常 OCR 路径（`pdf_ocr.go:112-119`）维护的是正确语义，两条路径不一致。
- 建议：`TextPages = len(nativePages) + len(ocrPages)`，构造 `PagesWithoutText` 时跳过 OCR 页；补“encode→decode 后摘要不变量与正常 OCR 一致”的测试。

#### AUD-012 非 owner 成员查看知识库统计，三项恒为 0

- 位置：[knowledge_base_service.go](../backend/internal/service/knowledge_base_service.go#L767) 的授权是 `kb.read`（viewer 即可），却把 actor 当 `ownerID` 传给 [knowledge_base_repository.go](../backend/internal/repository/knowledge_base_repository.go#L225)；四条统计查询全部带 `knowledge_bases.owner_id = ?`，其中文档数也被过滤。
- 影响：manager/viewer 看到“0 文档、0 浏览、0 提问”，连自己的浏览与提问也被吃掉；与 [API 设计](04-api-design.md#L785) 不符，前端会把有文档的库显示成空库。
- 建议：`kbID` 分支的文档查询改用 `knowledge_bases.id = ?`；浏览/提问保留 `user_id = actor`。

#### AUD-013 模型用量聚合包含已软删知识库

- 位置：[model_usage_repository.go](../backend/internal/repository/model_usage_repository.go#L89) 的 JOIN 只加 `reachableKnowledgeBaseCondition`，该条件（[knowledge_base_reachability.go](../backend/internal/repository/knowledge_base_reachability.go#L26)）不含 `deleted_at`；全库模式完全不加过滤。
- 影响：软删库的历史 token 与费用仍计入总量，`groupBy=knowledgeBase` 还会列出已删库名字；与质量接口口径（`chat_repository.go:910` 显式过滤）不一致。
- 建议：`scoped` 统一追加 `knowledge_bases.deleted_at IS NULL`。

#### AUD-014 `RecoverRunningJobs` 失败一次，文档 worker 永久退出

- 位置：[worker.go](../backend/internal/job/worker.go#L92) 在恢复失败后 `log.Error` 并 `return`；[main.go](../backend/cmd/server/main.go#L76) 该 worker 在 goroutine 中启动，无人重启；[storage_cleanup_worker.go](../backend/internal/job/storage_cleanup_worker.go#L70) 是同一模式。
- 影响：HTTP 正常、上传返回 201，但没有任何 goroutine 再领取任务；新文档永远 `pending`，旧的 `running` 永不恢复，只有一条 ERROR 日志，诊断接口也不报。
- 建议：失败按退避重试而不是 return；或启动失败即 Fatal（宁可起不来也不要半瘫）；把 worker 存活与积压暴露到 `/system/diagnostics`。

#### AUD-015 流式 `done` 之前同步生成标题，完成事件最多推迟 5s

- 位置：[chat_service.go](../backend/internal/service/chat_service.go#L1241) 在 `sink.Done`（[:1243](../backend/internal/service/chat_service.go#L1243)）之前调用 `updateSessionTitleIfNeeded`，标题超时为 5s。
- 影响：文本已流完但 `done` 未发出，前端仍显示“生成中”；此时断开，标题调用与落库已完成而 done 丢失。当前根配置 `TITLE_API_KEY` 为空，走首问摘要兜底，不产生网络等待；启用标题模型后才显现。
- 建议：先 `sink.Done`，再用 `context.WithoutCancel` 异步生成标题。

#### AUD-016 无优雅停机，HTTP 服务器无超时

- 位置：[main.go](../backend/cmd/server/main.go#L96) 只有 `ListenAndServe`，没有 `signal.NotifyContext`/`Shutdown`；`defer stopWorker()` 与 Redis 关闭在 SIGTERM 下不执行；未设 `ReadHeaderTimeout`/`IdleTimeout`（SSE 不应设 `WriteTimeout`）。
- 影响：滚动发布或 `docker stop` 时进行中的 SSE 被硬断，处理中的文档任务停在 `running`（只能靠 AUD-014 的恢复路径，而它自身可能失败）。
- 建议：`signal.NotifyContext` + 带超时的 `Shutdown`，之后停 worker、关 DB/Redis；补 `ReadHeaderTimeout`。

#### AUD-017 SSE 没有心跳帧

- 位置：[chat_handler.go](../backend/internal/handler/chat_handler.go#L523) 的 `sseSink` 只在有事件时写字节；检索阶段（尤其 rerank 长等待）零输出。
- 影响：前置 nginx/LB 的 idle 超时短于首事件耗时时，流被静默切断，客户端只拿到已发出的 delta，没有 done 也没有 error，只能靠前端超时兜底。
- 建议：等待检索时定期写 `: ping\n\n` 注释帧。

#### AUD-018 文档详情抽屉处理中每 2 秒清空片段列表

- 位置：[DocumentDetailDrawer.tsx](../frontend/src/pages/Documents/DocumentDetailDrawer.tsx#L183) 每 2s 轮询并 `setDocument(next)` 生成新对象；片段 effect 依赖整个 `document`（[:246](../frontend/src/pages/Documents/DocumentDetailDrawer.tsx#L246)），进入即 `setChunksLoading(true)`。
- 影响：处理中的文档每 2s 把片段区换成骨架屏，滚动位置、焦点、“重试片段”状态全部丢失，并多发一次 `GET /documents/:id/chunks`；用户无法在处理期间阅读已生成的片段。
- 建议：轮询结果按 `status/jobStatus/stage/progress/retryCount` 比较，相同不 set；片段 effect 依赖 `document.id` 与一个内容版本计数，而不是对象引用。

#### AUD-019 成员写操作成功、刷新失败被报成“写操作失败”

- 位置：[MembersPanel.tsx](../frontend/src/pages/KnowledgeBase/MembersPanel.tsx#L87) 的 `reload()` 无 try/catch；[:133](../frontend/src/pages/KnowledgeBase/MembersPanel.tsx#L133) 的 catch 把 `reload()` 的异常也报成 `'成员添加失败'`。删除路径先 `setDeleteTarget(null)` 再 `await reload()`，错误写进已关闭的对话框。
- 影响：写操作其实已生效，用户看到失败并重复提交（重复添加会得到另一种错误）；删除后的刷新失败完全不可见。
- 建议：reload 单独 catch，提示“已保存，但成员列表刷新失败，请重试”，与写失败分开；删除路径先刷新再关弹窗。

#### AUD-020 质量页切换知识库/周期沿用上一范围数据

- 位置：[QualityPage.tsx](../frontend/src/pages/Quality/QualityPage.tsx#L277) 与 [:283](../frontend/src/pages/Quality/QualityPage.tsx#L283) 只 `setPage(1); setGapPage(1)`，不清 `overview/feedback/gaps`；而统计范围切换在 [:330](../frontend/src/pages/Quality/QualityPage.tsx#L330) 显式清空三者。渲染条件为 `loading && !overview`（[:354](../frontend/src/pages/Quality/QualityPage.tsx#L354)），旧数据在位时加载态不出现。
- 影响：旧库数字、旧页反馈挂在新筛选下，分页器已显示第 1 页；弱网下可持续数秒，用户会据此做出错误判断。
- 建议：两条路径统一走 `resetAndReload()`，先清数据再加载。

#### AUD-021 会话列表后台刷新失败会替换已加载行

- 位置：[ChatSessionRail.tsx](../frontend/src/pages/Chat/ChatSessionRail.tsx#L171) 的渲染顺序是 loading → error 替换列表 → empty → list；[useChatSessions.ts](../frontend/src/pages/Chat/useChatSessions.ts#L113) 的 `sessionsError` 用 `query.isError`。
- 证据：用 `@tanstack/query-core` 实测，失败的后台 refetch 会得到 `status='error'`、`isError=true`、`isRefetchError=true`，同时旧 `data` 仍保留。因此错误分支会替换掉旧行。
- 影响：网络抖动时已有会话列表消失，只剩错误态；[交接](12-handoff.md#有效待办与部署边界) 已记录该风险，本轮确认成立。
- 建议：`isRefetchError` 时保留列表，用行内或顶部提示表示刷新失败；只有首次加载失败才整块替换。

#### AUD-022 重新生成的 `unconfirmed` 状态永远不会自动对账

- 位置：[useChatThread.ts](../frontend/src/pages/Chat/useChatThread.ts#L366) 的 `scheduleAutoChecks` 只由 `unconfirmedSend` 的 effect 调用（[:394](../frontend/src/pages/Chat/useChatThread.ts#L394)）；重新生成失败时设置 `{kind:'unconfirmed', autoChecksDone:0}`（[:707](../frontend/src/pages/Chat/useChatThread.ts#L707)），没有启动定时器。`checkRegeneration` 只有手动入口。
- 影响：[ChatPage.tsx](../frontend/src/pages/Chat/ChatPage.tsx#L1016) 用 `autoChecksDone > 0` 判断是否进入“需要决定”，而该值永远为 0，界面一直停在“正在确认重新生成结果…”，直到用户手动重试或刷新。与 [前端规范](10-frontend-spec.md#L271) 的 2s/5s 自动对账不符。
- 建议：把发送与重生成统一成一个待对账状态，复用同一套定时器；或在重生成 unconfirmed 时调用 `scheduleAutoChecks` 的泛化版本。

#### AUD-023 编辑较早的用户问题会静默删除其后全部消息，没有确认

- 位置：[ChatPage.tsx](../frontend/src/pages/Chat/ChatPage.tsx#L677) 的 `canEdit` 对任意用户消息为真，`startEdit`（[:435](../frontend/src/pages/Chat/ChatPage.tsx#L435)）没有位置判断或确认；后端 [chat_service.go](../backend/internal/service/chat_service.go#L1480) 收集目标之后的所有消息 ID，交给 `ReplaceMessageTail` 一并删除并重新生成。
- 影响：用户只想修正一句提问，却丢掉后面整段对话与分支；操作不可撤销。与 [前端规范](10-frontend-spec.md#L263) 要求的“编辑将删除后续消息”确认不符。
- 建议：仅当目标是最后一条用户消息时直接编辑；否则先确认“将删除其后 N 条消息并重新生成”，或提供“另开分支”的替代动作。

#### AUD-024 顶栏内联重命名失败会丢输入

- 位置：[InlineEdit.tsx](../frontend/src/components/ui/InlineEdit.tsx#L69) 的 `commit()` 先 `stopEditing()` 再 `onSubmit`；[ChatPage.tsx](../frontend/src/pages/Chat/ChatPage.tsx#L573) 的 `onSubmit` 失败时只提示错误。
- 影响：重命名请求失败（重名、网络、5xx）后编辑框已关闭，用户输入的内容丢失，只能重新打开重输；与 [前端规范](10-frontend-spec.md#L234) 的“失败保留输入”不符。
- 建议：`onSubmit` 成功后才退出编辑；失败保持编辑态并展示错误。

### P3

- **AUD-025 PDF 单页畸形导致整份永久失败；0 页 PDF 被归为“页数超限”。** 任一页 `readPage` 出错即包装成 `ErrCorruptFile`（[parser.go](../backend/internal/document/parser/parser.go#L179)），而 `corrupt_file` 是永久错误不重试，OCR 也拿不到救援（只处理无文字页）；`pageCount < 1` 与 `> MaxPDFPages` 共用 `ErrPDFLimit`（[:172](../backend/internal/document/parser/parser.go#L172)）。建议页级失败降级为该页无文本、超过阈值才整份失败；0 页单独返回损坏。
- **AUD-026 TXT/MD/DOCX 没有输出文本与切片数上限。** txt/md 直接 `os.ReadFile`（[parser.go](../backend/internal/document/parser/parser.go#L92)），DOCX 只限单 part 64MiB（[docx.go](../backend/internal/document/parser/docx.go#L28)），切片数无上限；50MiB 上传可产生上万切片，`rows` 与全部向量驻留内存后才发布。建议加 `MaxDocumentTextBytes`（与 PDF 对齐 8MiB）与 `MaxChunksPerDocument`，超限返回可分类的永久错误。
- **AUD-027 DOCX 缺少 XLSX 已有的 ZIP 结构校验。** [docx.go](../backend/internal/document/parser/docx.go#L88) 只 `zip.NewReader` 后取固定 part，不查条目数、重复名、加密标志；对照 [table.go](../backend/internal/document/parser/table.go#L198) 的 XLSX 校验。建议抽出 `validateOOXMLPackage` 复用。
- **AUD-028 上传未校验文件名长度/控制字符。** `CommitUpload` 原样写 `file.Filename`（[document_service.go](../backend/internal/service/document_service.go#L174)），列为 `VARCHAR(255)`（`migrations/001_init_schema.sql:32`），超长时 INSERT 失败走补偿删除并返回 500；重命名路径已有 255 上限校验。建议 `validateFile` 复用同一规则并前置 400。
- **AUD-029 超宽表格行对每个单元格都单独成 chunk。** [splitter.go](../backend/internal/document/splitter/splitter.go#L899) 对全部单元格循环，即使只有一个超预算，也生成 10 个各含一格、其余列为空的 chunk，引用定位只覆盖那一格。建议只切超预算单元格，其余合并重建行。
- **AUD-030 provider 流式观察器的 `lineBuffer` 无上限。** [openai.go](../backend/internal/provider/chat/openai.go#L319) 的 `body` 有 4MiB 上限，但非 SSE 的单行超长响应会无限累积到 `lineBuffer`。建议设上限，超限判定不可解析并停止累积。
- **AUD-031 管理员变更响应恒返回 `ownedKnowledgeBaseCount: 0`。** mutation 响应复用 `AdminUserResponse`，构造器只在列表路径赋值（[admin_user_service.go](../backend/internal/service/admin_user_service.go#L231)）。前端目前只读列表行，暂无功能影响；建议 `omitempty` 或改指针。

## 优化建议

1. **拆 `chat_service.go`**：2486 行、约 80 个函数，会话/质量/用量/导出/发送/重生成/意图/标题全在一个文件，是字段漂移（`AUD-007`）的温床。按“会话管理、发送与生成、质量与用量、导出”拆四个文件，先搬移不改行为。
2. **去掉自动范围每轮固定 N+1**：[chat_multi.go](../backend/internal/service/chat_multi.go#L54) 对每个召回项重复鉴权，`chat_service.go` 再逐库查 answer config；用已加载的 `bases` 建 map 判断可达性，配置一次批量读。`chat_quality_issue.go:118/197/203` 三次鉴权合并为一次。
3. **上传路径只读一遍**：hash、表格预览、校验解析、保存各读一次 50MiB；改为一次流式读并落临时文件复用，hash 顺手计算。
4. **OCR 批量渲染**：[local.go](../backend/internal/document/ocr/local.go#L94) 每页起一次 `pdftoppm`，40 页等于 40 次全文件解析加 40 次 Tesseract 冷启动；按连续页区间一次渲染。
5. **XLSX 只校验关键 part**：[table.go](../backend/internal/document/parser/table.go#L216) 对每个 XML 全量流式校验后又交给 excelize 解析一遍；把 token/depth 校验限定到 `sheet*.xml`/`sharedStrings.xml`。
6. **迁移工具**：[migrate/main.go](../backend/cmd/migrate/main.go#L33) 改为单文件超时、增加 `schema_migrations` 台账、`-dir` 显式目录（当前 `Glob("migrations/*.sql")` 依赖 CWD，异地执行只报 "no migration files"）。
7. **doctor 与 server 对齐**：[doctor/main.go](../backend/cmd/doctor/main.go#L16) 先跑 `cfg.Validate()`，再复用导出的只读 schema 断言；否则会在 server 必然起不来的库上报健康。
8. **可观测性**：日志补 level、request id、user id（[middleware/logger.go](../backend/internal/middleware/logger.go#L10)）；限流 Redis 故障 fail-open 时出指标；诊断增加三个 worker 的存活与积压。
9. **前端外壳与会话列表**：[AppShell.tsx](../frontend/src/layouts/AppShell.tsx#L94) 依赖整个 `props` 对象，任何页面 state 变化都重注册；会话列表刷新重取所有已加载页（`reloadSessions`）。前者按字段比较，后者只刷首屏。
10. **清理死代码**：`blockingFallback`、`loadAllMessages`、`onlyPage` 恒 false 分支、`.ui-page-head*` 与 `.rail__item-count`、`homeData` 两个无人调用的 loader、前端 `DOCUMENT_PROCESS_FAILED` 映射。
