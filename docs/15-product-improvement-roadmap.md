# 产品改进路线图

## 目标

本路线图面向已经可用的企业知识库问答产品，后续投入优先解决三件事：

1. 用户能判断文档是否真正进入知识库，并能从失败或取消中恢复。
2. 运营人员能发现低质量回答和知识缺口，而不是只看到零散点赞/点踩。
3. 企业部署者能判断依赖服务和任务队列是否健康。

不以视觉重构、复杂聊天版本树、多模型市场或与问答闭环无关的功能为目标。

## 产品原则

- 可信优先：进度、成功和错误状态必须来自真实服务端状态，不模拟完成。
- 恢复优先：失败、取消和结果未知必须有不同语义和对应操作。
- 证据优先：质量判断要保留回答、引用、知识库和检索降级信息。
- 渐进交付：每个阶段都能独立上线、回滚和度量，不依赖一次性大改。
- 权限继承：所有文档、回答和运营数据继续通过知识库 owner/member 边界访问。

## 阶段计划

### P1 文档处理可观测性与恢复

目标：让用户准确知道文件处于哪个步骤、完成了多少、为何停止以及下一步能做什么。

交付范围：

- 持久化后台处理进度；解析、切片和 Embedding 使用连续且单调的 0-100 数值。
- Embedding 按真实批次完成量推进，不在长任务中固定停留于 75%。
- 取消任务在界面中显示为“已取消”，不再与处理失败混淆。
- 自动重试继续展示重试次数和下一次尝试时间。
- 保留取消、重新处理和失败原因，并覆盖取消/发布、重试/进度并发回归。

验收标准：

- 服务重启或页面刷新后进度不会退回阶段默认值。
- 处理进度只前进；完成为 100%，新任务为 0%。
- 被取消任务不会展示红色“处理失败”，且可以重新处理。
- 旧数据库应用 migration 后能为现有任务生成合理初始进度。

### P1 RAG 质量运营闭环

目标：把已有的回答赞/踩转化为可处理的知识维护队列。

交付范围：

- 质量概览：回答量、反馈覆盖率、好评率、负反馈数量、无引用回答数量。
- 负反馈列表：按知识库、时间和是否有引用筛选，展示回答、问题、引用与 rerank fallback。
- 知识缺口列表：聚合无引用、依据不足和连续改写问题。已交付为两个类别
  `no_citations` 和 `repeated_rewrite`。对知识型提问，「无引用」和「依据不足」是同一个
  条件——citations 由 rerank 结果推导，固定拒答话术恰好在结果为空时使用，所以不拆成两类。
  真正独立的第三种情况是「有引用但模型仍拒答」，它需要判定回答文本，属于本文档 P2 的
  回答质量评估，本轮不做。
- 从问题项直接跳转原会话和引用文档。

验收标准：

- 统计与列表只包含当前用户有权访问的知识库。
- 指标口径写入 API 文档，空数据与分页行为稳定。
- 运营人员能从一条负反馈定位到原问题、回答和引用来源。

### P1 部署健康与诊断

目标：在用户报错前识别模型、Redis、MinIO、数据库或任务队列异常。

交付范围：

- 管理诊断页展示数据库、Redis、MinIO 和模型 Provider 的可用状态。
- 展示 pending/running/failed 任务数、最老排队时间和近期失败率。
- 记录检索耗时、首 token 延迟、完整生成耗时及 Provider fallback。
- 健康检查不得返回密钥、连接串或 Provider 原始敏感错误。

### P2 首次使用与知识库质量

- 创建知识库后直接引导上传文档，处理完成后提示可开始提问。
- 检测同知识库内的重复文件内容，并由用户决定替换或保留。
- 支持文档版本替换、过期提醒和解析异常提示。
- 区分“知识库没有依据”“检索失败”和“模型拒答”。

### P2 权限与协作

- 在现有 owner/member 能力上明确 viewer/editor/manager 行为矩阵。
- 下载、导出、反馈运营数据和永久删除分别校验权限。
- 对所有资源 ID 增加跨用户、已删除知识库和成员撤销后的契约测试。
- 暂不引入复杂组织树、SSO 或通用策略引擎。

### P2 搜索、移动端与无障碍

- 完善搜索建议、结果定位和无结果建议。
- 验证触摸目标、移动端输入法、软键盘和长引用布局。
- 流式回答、进度和错误状态使用克制的 live region 播报。
- 键盘操作后恢复合理焦点，弹窗和抽屉关闭时返回触发元素。

## 度量指标

| 指标 | 说明 | 第一目标 |
| --- | --- | --- |
| 文档处理成功率 | 完成任务 / 已终止任务 | 可按日观察趋势 |
| 文档处理 P95 时长 | 上传完成至可问答 | 分阶段可定位 |
| 失败恢复率 | 失败或取消后重新处理并完成 | 可追踪 |
| 反馈覆盖率 | 有评价回答 / 全部回答 | 建立基线 |
| 负反馈闭环时间 | 负反馈产生至知识维护完成 | 可追踪 |
| 无引用回答率 | citations 为空的知识型回答占比 | 可解释并下降 |
| 首 token P95 | 请求开始至首个 delta | 可分 Provider 观察 |

## 实施顺序

当前从“P1 文档处理可观测性与恢复”开始。其数据库和 API 契约稳定后，再实现 RAG 质量概览与负反馈工作台；健康诊断依赖同一批任务度量字段，排在质量闭环之后。

进度：

- P1 文档处理可观测性与恢复：已完成。
- P1 RAG 质量运营闭环：已完成（质量概览、负反馈列表、知识缺口列表）。
- P1 部署健康与诊断：已完成（`/system/diagnostics`、依赖感知的 `/healthz`、`/diagnostics` 页面）。四项交付均已落地，口径见 `04-api-design.md` 的“系统诊断”。
- P2 首次使用与知识库质量：已完成（上传引导闭环、内容查重、版本替换与过期提醒、解析异常分类、四类回答状态）。四项交付均已落地，契约见 `04-api-design.md`。
- P2 权限与协作：未开始，是下一项。

P1 部署健康与诊断的两处刻意偏离：

- **Provider 不做主动探测。** OpenAI 兼容接口没有免费的 ping，为检查而发 completion 会
  让运维每次打开页面付一次钱，且测出的延迟不是真实请求的延迟。改为报告配置完整性加真
  实流量观察到的健康度。
- **接口只要求登录，没有按角色限制。** JWT 无角色声明、无角色中间件、唯一种子用户是
  `role: "user"`，加管理员校验会把现有部署全部锁在自己的诊断之外。响应体口径因此更保
  守。补齐角色模型后再收紧，列为下面的 P2 待办。

P2 首次使用与知识库质量的四处刻意偏离：

- **`answer_status` 不回填历史数据。** 无法从已有列推断一条 019 之前的回答当时是检索失败
  还是没有命中，猜出来的分类比空着更糟。历史行留在 `no_citations` 里，因此
  `retrievalFailedTotal` / `modelRefusedTotal` 为 0 只表示"尚未观察到"。
- **`model_refused` 依赖模型遵从提示，天然少报。** 识别标记而不用启发式：启发式会把"根据
  资料，X 不适用于 Y"这种正常回答误判成拒答。识别不到标记就算 `answered`，宁可少报不可
  误报，所以这一类的计数是下限。
- **替换是新建 + 归档，不是原地覆盖。** 原地覆盖会让一次失败的重新解析毁掉本来可用的文
  档：旧 chunk 已删、新 chunk 没建出来。旧文档保留为历史版本，仍可从引用追溯。
- **过期只提醒，不降权也不删除。** 文档旧不等于内容错。静默降权会让检索结果无法解释，所以
  `isStale` 完全不参与检索。

## P2 待办：诊断接口的角色限制

现状是 JWT 只带 `UserID`，没有角色声明，也没有角色中间件。补齐顺序：

- JWT 增加角色声明，登录与刷新路径同步写入。
- 增加角色中间件，并为现有部署提供把首个用户提升为管理员的迁移或运维步骤。
- 把 `GET /api/v1/system/diagnostics` 移到管理员组。迁移路径落地之前不能移，否则现有
  部署会失去自己的诊断入口。

即便完成收紧，响应体的"不返回什么"约束仍然有效：它保护的是日志与响应的边界，与谁能访
问无关。
