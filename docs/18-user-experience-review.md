# 用户体验评审与改进建议

评审日期：2026-11-23。状态：**第一批改进本地实现完成，其余建议待取舍**（见第 8 节；以下原始观察保留评审时语义）。

本次从普通使用者与资料维护者的任务出发，评估知汇在首次提问、资料导入、问答、来源核对和问题跟进中的体验。本文记录观察、建议及候选验收标准；现行行为仍以 [产品说明](01-prd.md) 和 [前端规范](10-frontend-spec.md) 为准。

## 1. 核心判断

项目已具备自动与指定范围问答、引用原文定位、后台上传、错误恢复、历史会话、回答版本、收藏、版本对比和质量跟进等能力。当前最值得投入的是让这些能力更容易被发现，并连成用户能够直接完成的任务：

1. 开始前，知道现有资料能回答什么。
2. 操作时，明确正在总结、对比或询问哪些资料。
3. 阅读时，知道答案依据、版本和适用条件。
4. 答不上来时，能够就地采取下一步行动。

这些优先级来自页面体验和产品判断，尚未经过真实用户访谈或任务完成率验证。

## 3. 主要改进建议

### 3.1 让总结、对比和制度查询成为完整操作

**关联需求：R03–R05。建议优先处理。**

**用户场景与当前表现：** 用户点击「总结一份资料」，自然期待先确定目标资料。页面实测中，该按钮只向输入框追加「请总结资料中的关键要点，并标注引用来源。」，范围仍为自动跨库，没有要求选择文档。代码中的「对比文档差异」「查找制度规定」采用相同的通用文字追加方式。

**建议：** 总结先选择资料和输出形式；对比先确定两份资料及比较事项；制度查询先明确主题或适用对象。复用已有指定文档选择器，生成的问题允许继续编辑。

**候选验收标准：**

- 发送前能清楚看到目标文档和提问范围；需要选择资料时提供明确引导。
- 用户无需自行组织完整提示词，就能完成总结或对比。
- 对比结果能区分两份资料；资料未提及的内容明确标注，不补造差异。
- 仅检索到部分片段时，说明覆盖限制，不把局部内容表述为全文结论。

代码依据：[ChatPage](../frontend/src/pages/Chat/ChatPage.tsx) 的 `onSuggest`（约第 700 行）及 `ChatEmptyState` 三个建议按钮（约第 984 行）。

### 3.2 导入完成后直接针对本次资料提问

**关联需求：R02。建议优先处理。**

**用户场景与当前表现：** 用户刚导入一份制度，希望立即问这份资料。代码中，上传任务和文档页导入结果的「开始提问」仅传知识库 ID，进入整库问答；文档详情和列表勾选入口则传文档 ID，能够限定资料。详情入口已在页面确认，上传完成状态本次未重新实测。

**建议：** 单份资料提供「问这份资料」，批次结果提供「问本次导入」；整库问答另标为「在整个知识库提问」。这是入口语义与任务范围的改进，现有整库行为不构成越权问题。

**候选验收标准：**

- 提问入口带入用户选定的本次资料，聊天页明确显示文档范围。
- 尚未处理完成、失败或不可访问的文档有清楚说明，不静默排除或扩大范围。
- 批次超过现有 20 份文档、5 个知识库上限时要求用户选择子集。
- 保留整库提问入口，并能从名称判断其含义。

代码依据：[DocumentImportProvider](../frontend/src/pages/Documents/DocumentImportProvider.tsx) 第 191 行；[DocumentsPage](../frontend/src/pages/Documents/DocumentsPage.tsx) 第 496、502、517 行；[DocumentDetailDrawer](../frontend/src/pages/Documents/DocumentDetailDrawer.tsx) 第 507 行；[documentChatScope](../frontend/src/pages/Chat/documentChatScope.ts) 的 `documentChatUrl`。

### 3.3 首页说明当前能问什么

**关联需求：R01、R09。建议优先处理。**

**用户场景与当前表现：** 普通员工进入首页，主要想查询制度或业务知识。当前首页使用固定的入职问题示例，快捷操作为新建知识库、导入文档和查看会话。新对话已有知识库名称和描述，但用户仍需猜测可问的问题以及资料是否就绪。

**建议：** 提问框附近展示可用主题、可问答状态和少量与实际资料对应的问题。普通使用者优先看到提问和继续历史任务；维护者保留建库、导入等操作。

**候选验收标准：**

- 示例对应当前用户可访问且可用于问答的资料，不暗示不存在的内容。
- 区分有可用资料、空库、处理中、读取失败等状态；访问权限提示基于可确认的信息。
- 状态变化或进入资料管理时保留已输入的问题。
- 不需要用户先理解知识库管理，就能完成第一次有效提问。

代码依据：[HomePage](../frontend/src/pages/Home/HomePage.tsx) 第 96、107、188 行；[ChatPage](../frontend/src/pages/Chat/ChatPage.tsx) 的 `ChatEmptyState`；[PrimaryNav](../frontend/src/components/navigation/PrimaryNav.tsx) 第 39 行。

### 3.4 无法回答后提供就地下一步

**关联能力：现有个人问题跟进；与 R08 团队交接相关，但不等同于实现 R08。建议优先处理。**

**用户场景与当前表现：** 已有「那保险呢」历史问答明确说明缺少依据，回答附近主要是来源、复制、收藏、评价和重新生成。质量运营里已经有补资料、保存测试问题、跟进和复测，当前聊天回合与这些动作的连接不够直接。

**建议：** 根据实际原因提供「选择相关资料」「补充问题背景」「跟进这个问题」等动作，带入原问题。继续区分缺少依据、检索服务故障和模型拒答。补资料操作遵守现有权限；团队交接另按 R08 确定共享内容和接收人。

**候选验收标准：**

- 无法回答时，用户能在当前回合找到与原因匹配的下一步。
- 调整资料范围时保留问题，并明确进入的新会话范围。
- 跟进可定位原问题和确切回答，保留现有补资料、复测和手动解决流程。
- 不把检索故障统一归因于资料缺失，不自动分享私人会话。

**待专项核对的观察：** 个人自动跨库缺口中的出差保险问题被标在「【演示】技术运维」，补充资料链接也指向该库。前端按返回的 `item.knowledgeBaseId` 生成链接；尚未确认历史数据归属的根因。建议自动或多库缺口说明实际范围，并让用户确认补资料的目标库，不将此观察直接定性为后端错误。

代码依据：[answerStatus](../frontend/src/pages/Chat/answerStatus.ts) 的 `no_basis`；[ChatMessage](../frontend/src/pages/Chat/ChatMessage.tsx) 第 192、218 行；[QualityPage](../frontend/src/pages/Quality/QualityPage.tsx) 的 `GAP_PRESENTATION` 和缺口操作区。

### 3.5 在回答附近展示来源新旧状态和生效规则

**关联需求：R06、R07。R06 原草案为 P1，R07 为 P2；本次不修改原优先级。**

**用户场景与当前表现：** 用户再次打开历史制度答案，可能直接阅读或复制。原文预览里已经有版本状态、查看差异、按当前有效资料提问等能力，但需要主动打开来源才能发现。设置页说明了自动或多库问答与手动单库回答配置的差别，聊天中主要展示资料范围。

**建议：** 在回答附近汇总「有来源已更新」，复用已有版本比较和重问入口；范围旁简要说明系统规则或本库规则是否生效。固定范围调整时，明确告知会进入新会话并保留问题。

**候选验收标准：**

- 已确认的来源更新在答案附近可见，查询失败或状态未知不显示为版本有效。
- 历史答案及其原始依据保持可核对，不静默替换引用。
- 回答规则说明与现行自动、单库、多库和指定文档合同一致，不擅自改变继承规则。
- 「当前已发布版本」与「业务制度仍然有效」分别表达。

代码依据：[ChatSourcePreview](../frontend/src/pages/Chat/ChatSourcePreview.tsx) 第 148 行；[CitationVersionNotice](../frontend/src/pages/Chat/CitationVersionNotice.tsx) 第 29 行；[ChatPage](../frontend/src/pages/Chat/ChatPage.tsx) 第 551 行。规则依据见 [前端规范](10-frontend-spec.md#知识库详情页)。

### 3.6 降低日常维护所需的技术知识

**关联需求：R09。建议后续完善。**

**用户场景与当前表现：** 资料维护者进入设置页，首先看到向量召回数量、精排数量和相关度；回答配置还展示 `CHAT_ALLOWED_MODELS`、Provider 默认值等术语。日常工作更常围绕回答风格、资料就绪状态与成员访问。

**建议：** 默认突出日常维护设置，将检索参数收进高级检索，用「找不到内容」「无关资料太多」解释调整目的。模型覆盖不可用时，使用「当前使用管理员配置的模型」等业务文案。按已有权限调整入口主次。

**候选验收标准：** 普通使用者容易找到提问、历史与收藏；维护者容易找到导入、回答配置和成员；高级参数仍可访问，字段含义清楚；不新增角色体系或改变服务端授权。

代码依据：[KnowledgeBaseSettingsPage](../frontend/src/pages/KnowledgeBase/KnowledgeBaseSettingsPage.tsx) 第 60 行；[RetrievalConfigForm](../frontend/src/pages/KnowledgeBase/RetrievalConfigForm.tsx) 第 101 行；[AnswerConfigForm](../frontend/src/pages/KnowledgeBase/AnswerConfigForm.tsx) 第 82 行。

## 5. 回答完整性应独立保障

[BENCH-RAG-001 历史基线](14-verification.md#bench-rag-001性能与回答质量基线2026-11-21)在 36 个固定合成问题中，33 个严格完整、3 个部分完整；E05 漏掉超标费用的书面批准条件，9 个缺资料问题未编造所求值。该结果仅适用于当时的样本、模型和环境，本次没有重跑。

用户执行制度时，审批条件、适用对象、金额、时限和例外都会影响答案是否可采用。建议沿用现有问题集，分别核对「有依据」「完整」「可执行」，优先回归已发现的遗漏，并加入代表性业务资料验证。出现引用只能证明有来源入口，不能替代答案完整性核对。

这一事项继续归属 [有效待办](15-backlog.md#尚未关闭的工程事项) 的 BENCH-RAG-001-Q。本次不新增同义待办、不调整全局阈值，也不将历史部分通过写成当前已修复。

## 6. 候选推进顺序与用户验证

根据本次任务衔接观察，建议先评估以下三条路径：

1. 明确资料对象的总结与对比：R03、R04，并复用 R05 的任务引导方式。
2. 导入完成后针对本次资料提问：R02。
3. 无依据后连接已有个人跟进、补资料与复测；团队交接继续按 R08 单独决定。

首页主题与就绪状态可作为下一项；搜索默认动作与已保存配置说明可独立安排。回答完整性的已知问题持续跟进，不以界面优化替代质量回归。

这与 2026-11-18 草案「R01、R02、R06 先行」的建议顺序不同，是供选择的更新建议。两者均未获排期确认，最终顺序应在需求草案的待决定事项中统一确定。

有测试用户后，优先观察以下任务，不提前编造完成率或时间目标：

| 用户任务 | 观察点 |
| --- | --- |
| 首次进入后查询一条制度并核对出处 | 是否知道能问什么、是否选错范围、能否找到对应来源 |
| 导入一份资料并针对它提问 | 是否理解处理状态、是否需要重新选资料、是否意外进入整库范围 |
| 总结或对比资料 | 是否需要额外讲解或手写复杂提示词、能否明确目标和覆盖限制 |
| 遇到无依据回答后继续处理 | 能否找到可执行下一步、是否选对补资料的库、跟进能否回到原问题 |
| 再次使用历史制度答案 | 能否发现来源更新、区分已发布版本与业务有效性 |
