# Redis 故障等待修复与业务语料 Rerank 校准

日期：2026-09-28。用户要求先处理 Redis 故障时的等待，再做现有业务语料的 Rerank 校准。

## Redis 修复与验证

原客户端只设置地址、密码与 DB，沿用 go-redis v9.20.0 的命令重试和连接重试。连接拒绝后，缓存 GET、SET 和限流分别重复等待，故障请求仍能完成，但增加了不必要的延迟。

现在由 `cache.Open` 为缓存、限流和诊断建立共享的故障保护：

- `REDIS_OPERATION_TIMEOUT=200ms`：单次 Redis 命令的总预算，覆盖连接、握手、连接池与读写；尊重更短的调用方 deadline，关闭命令及连接自动重试。
- `REDIS_FAILURE_COOLDOWN=5s`：连接/超时失败后暂停访问；到期仅一个命令探测，成功恢复，失败重新冷却。旧在途请求的迟到成功不会提前结束新故障的冷却。
- 冷却期直接返回错误，沿用原策略：缓存降级为调用 Embedding，限流 `open` 放行、`closed` 返回503。
- 请求自身取消不认定为 Redis 故障；缓存未命中、Lua `NOSCRIPT` 等服务端正常响应不触发冷却。握手内部命令共享外层预算，避免恢复探测被自己的保护逻辑拒绝。

| 同机连接拒绝测试 | 原客户端 | 修复后 |
| --- | ---: | ---: |
| 首次 GET | 1724ms | 52ms |
| 随后 SET | 1719ms | <1ms，冷却跳过 |
| 随后限流 | 1683ms | <1ms，冷却跳过 |
| 再次 GET | 1714ms | <1ms，冷却跳过 |
| 再次 SET | 1701ms | <1ms，冷却跳过 |

这是一次同机故障对照，不是吞吐或端到端问答基准；0ms原始记录表示按毫秒取整后小于1ms。

真实 Redis 3.2.100 使用独立 `127.0.0.1:16379`，关闭持久化。正常时缓存命中、限流第二次429；停止后缓存检测到故障，`open` 返回200、`closed` 返回503，冷却期没有再次等待；重启并到期后缓存再次命中，限流恢复200/429。共享 Redis 未停止，临时进程已退出。

本地回归包含接收连接但不响应的服务、恢复握手、缓存命中/过期、Lua首次加载、并发单探测、迟到成功和取消请求。`go test ./...`、`go vet ./...`、`go test -race ./internal/cache` 通过。环境参数见 [配置规范](08-env-config.md#redis-限流与-query-embedding-缓存)；部署时需重新构建并重启后端，新默认值才生效。

## 校准语料与方法

使用当前业务知识库已发布的89个片段，没有新建或重建向量：

| 文档 | 片段数 |
| --- | ---: |
| Linux环境安装配置nodejs详细教程_linux安装nodejs-CSDN博客.pdf | 6 |
| 7.1.Mysql.md | 83 |

数据库连接显式只读；未迁移public、未启动业务worker、未修改知识库配置。真实调用使用 `Qwen/Qwen3-Embedding-4B`（1536维）、`Qwen/Qwen3-Reranker-4B`。每题通过生产检索服务执行混合召回 Top30，再真实精排，保持strict且无降级。为排除 Redis 对评分的影响，校准服务未接入缓存。

在取得模型分数之前固定40题及证据标注：28题有答案，12题当前语料中无答案。有答案题含6道需要多个证据组的问题；无答案题含8道主题相近但缺少具体信息的问题，以及4道域外问题。提前固定调参集和复核集，各20题（14有答案、6无答案）。

“完整证据覆盖”要求每个必要证据组至少保留一个片段；标注由本次任务根据当前原文编写，尚未经业务人员确认，不是对原文技术准确性的审核。复核集仍来自同一批文档，只能验证同语料内的问题泛化，不能代表新文档或整个企业业务。

对每题保存的真实分数离线回放55组配置：TopK为1/3/5/8/10，阈值为0/0.3/0.5/0.7/0.8/0.9/0.95/0.98/0.99/0.995/0.999。按生产顺序先截TopK，再按阈值过滤。只用调参集选择：优先保留最多完整证据，其次拒绝更多无答案题，最后减少上下文字符。复核集不参与参数选择。

## 结果

调参集选出当前语料的候选：`vectorTopN=30`、`rerankTopK=3`、`scoreThreshold=0.95`，混合召回和Rerank均启用。

| 指标 | 调参集默认5/0.3 | 调参集候选3/0.95 | 复核集默认5/0.3 | 复核集候选3/0.95 |
| --- | ---: | ---: | ---: | ---: |
| 有答案题完整证据覆盖 | 14/14 | 14/14 | 14/14 | 14/14 |
| 无答案题被检索阈值拒绝 | 5/6 | 6/6 | 4/6 | 4/6 |
| 其中近域无答案题被拒绝 | 3/4 | 4/4 | 2/4 | 2/4 |
| 每题平均片段数 | 2.85 | 1.45 | 3.30 | 1.85 |
| 每题平均片段字符数 | 1723 | 969 | 1833 | 1003 |

复核集上下文字符约减少45.3%，必要证据覆盖没有下降。字符数仅计选中片段正文，包含拒绝后零片段的问题；不是token数、账单节省或回答准确率。TopK=1在调参集丢失一道题的完整证据，因此没有选择它。

补充排序指标：首个标注证据的MRR，融合召回调参集0.9167、复核集0.9286，真实精排后两组均0.9643。融合Top5与精排默认Top5均已完整覆盖28道有答案题，不能把此次校准描述为新增了答案召回。

复核集仍有两道无答案题保留上下文：

| 问题 | 精排最高分 | 为什么没有答案 |
| --- | ---: | --- |
| 教程里的 Node.js 18.20.3 安装包占用多少 MB？ | 0.989012 | 资料有版本与下载地址，没有安装包大小 |
| MySQL 笔记所述优化在本公司压测中把 TPS 从多少提升到多少？ | 0.963485 | 资料仅有“提升数倍”的泛化描述，没有本公司压测数值 |

这两题证明相关性高分不等于包含所需事实。没有根据复核结果继续抬高阈值重新调参，也不把检索阶段误放行称为模型已经幻觉。

选定参数后，另外对两道跨片段题及上述两道无答案题按候选配置重新执行4次真实生产检索。两道有答案题仍覆盖全部证据组，所有结果均满足TopK≤3、分数≥0.95；两道无答案题仍各保留一个片段，与首次回放的边界一致。

## 回答边界复核

对上述两道无答案题，以及“下载命令+NODE_HOME”和“余额快照读+UPDATE”的两道跨片段题，分别使用默认和候选上下文，直接调用生产 `buildAnswerMessages` 与真实 `deepseek-v4-flash`，共8次回答调用。未绕过生产回答提示词，没有数据库或消息写入：

- 两种配置下，跨片段回答均包含关键下载/环境变量命令，或当前读/乐观锁解决方式。
- 两种配置下，两道无答案题都明确表示“无法从当前知识库确认”，没有编造安装包MB数或TPS前后数值。
- 这是4题的默认非流式回答提示词复核，不代表全量回答准确率，也不包含本轮意图分类、历史对话、标题或新浏览器验收。
